## 算法原理

「时间测试」指不依赖评测机（OJ），在本地直接测量一段程序实际消耗的时间，从而判断它能否在时限内通过、以及不同写法之间的快慢。

核心工具是 C++ 标准库 `<ctime>` 提供的 `clock()` 函数与常量 `CLOCKS_PER_SEC`。`clock()` 返回自程序启动以来（或某个实现定义的起点）消耗的**处理器时间**（CPU 时间）的计数值；`CLOCKS_PER_SEC` 表示该计数值每秒钟对应的数量，即「时钟滴答」数。于是，先在被测代码执行前后各取一次计数值，两者之差除以 `CLOCKS_PER_SEC`，就得到这段代码消耗的秒数。

这里需要区分两点：`clock()` 统计的是 **CPU 时间**而非「墙上钟表时间」——程序因睡眠、等待输入、I/O 阻塞而挂起的时间不会被计入；因此它更适合衡量「这段代码真正干了多少活」，而不是「从开始到结束过了多久」。对竞赛中估测算法运行耗时而言，前者通常正是我们关心的对象。

## 核心公式 / 状态定义与转移方程

设被测代码块执行前后分别调用 `clock()` 得到两个计数值 $C_1$ 与 $C_2$，则这段代码消耗的处理器时间（单位：秒）为：

$$
t = \frac{C_2 - C_1}{\text{CLOCKS\_PER\_SEC}}
$$

其中 `CLOCKS_PER_SEC` 是 `<ctime>` 中定义的常量，表示 `clock()` 返回值每秒钟对应的计数值；不同系统上它的取值可能不同（常见为 $10^6$ 或 $10^3$），因此**不要**在代码里写死它的数值，一律使用该常量。

由于 `clock()` 返回整数计数，$C_2 - C_1$ 可能为 $0$（代码跑得太快、低于一个时钟滴答），此时测出的时间为 $0$，说明这段代码执行时间过短，需要把它放进循环里多跑若干次再取平均，才能得到有意义的测量值。

## 逐行代码解析

以下是最基本的计时框架（关键用法 / 伪代码，非可运行程序）：

```cpp
#include <ctime>                                      // 提供 clock() 与 CLOCKS_PER_SEC

clock_t t1 = clock();                                 // 第 1 次计时：记录起点
// 在这里放入要测量的程序主体
clock_t t2 = clock();                                 // 第 2 次计时：记录终点
double elapsed = (double)(t2 - t1) / CLOCKS_PER_SEC;  // 换算成秒
```

几个关键点：

- `clock()` 的返回类型是 `clock_t`（通常为整数类型），直接相减得到两个计数值之差，再除以 `CLOCKS_PER_SEC` 得到秒数；注意分子要先转成 `double`，避免整数除法把结果截断成 $0$。
- 计时范围必须严格覆盖被测代码：`t1` 取在主体之前、`t2` 取在主体之后，中间不要夹带无关的输入输出，否则会把 I/O 时间也算进去。
- 若代码运行时间极短，一次测量可能得到 $0$，可将被测代码整体放入循环重复 $m$ 次，再用总时间除以 $m$ 得到单次平均耗时。

## 复杂度分析

「时间测试」是一个观测工具，本身不改变被测算法的复杂度：`clock()` 每次调用是 $O(1)$ 的常量开销，两次计时几乎不引入额外成本。测量得到的数值取决于被测代码自身，因此本知识点的时间、空间复杂度**视具体实现**。

- **时间复杂度**：视具体实现。计时框架只是两次 $O(1)$ 调用，实际运行时间由被测算法决定。
- **空间复杂度**：视具体实现。计时框架只额外使用常数个变量（$O(1)$），其余空间全部来自被测算法。

## 适用场景

- **本地估时**：在本地（而非 OJ）大致判断某份代码会不会超时，避免「交上去才超时」。
- **比较不同写法**：对同一问题的多种实现各测一遍，横向对比谁更快，辅助选择与优化。
- **暴力卡时（骗分）**：在暴力程序里设置一个时限阈值，运行到接近超时时立刻结束并输出当前最优答案，从而在保证不超时的前提下尽量多拿部分分。
- **调试定位**：分别测出程序各阶段（读入、预处理、核心计算、输出）的耗时，定位性能瓶颈。

## 常见陷阱与注意事项

1. **`clock()` 测的是 CPU 时间，不是墙上时间**：程序睡眠、等待输入或被操作系统暂停的时间不会被计入；若要测量「从开始到结束的真实经过时间」，应改用 `std::chrono` 的 `steady_clock`。
2. **整数除法截断**：`(t2 - t1) / CLOCKS_PER_SEC` 若分子是整数，会先做整数除法再隐式转换，结果恒为 $0$；务必把分子先转成 `double` 再除。
3. **不要写死 `CLOCKS_PER_SEC` 的数值**：它在不同系统上的取值可能不同，必须使用常量本身，否则换算出的秒数会出错。
4. **计时区间要干净**：把无关的输入输出、文件读写夹在 `t1` 与 `t2` 之间，会把 I/O 时间混进测量结果。
5. **太短测不出**：单次运行时间低于一个时钟滴答时会得到 $0$，需循环多次取平均；计时函数自身也有极小的系统误差，短代码要多测几遍、剔除明显异常值。
6. **编译选项影响结论**：不同优化级别（如 `-O2`）下代码运行速度差异很大，对比不同写法时应在相同编译选项与相同环境下测量。

## 对比与扩展

| 方法 | 测量对象 | 特点 |
|---|---|---|
| `clock()` + `CLOCKS_PER_SEC` | CPU 时间 | 简单直观，适合估算算法耗时 |
| `std::chrono::steady_clock` | 墙上时间（单调时钟） | C++11 起推荐，精度高、不受系统改时间影响 |
| `std::chrono::high_resolution_clock` | 平台可用的最高精度时钟 | 精度最高，但不同平台语义略有差异 |
| `gettimeofday` / `QueryPerformanceCounter` | 墙上时间 / 高精度计数 | 平台相关，竞赛中不如前两者通用 |

扩展方向：

- **卡时暴力**：在暴力、搜索或随机化算法里，每次迭代前用 `clock()` 检查已用时间，一旦超过阈值（如题目时限的 $90\%$）立即停止并输出当前最优解，避免超时后连部分分都拿不到。
- **对拍测速**：把计时写进对拍脚本或 `stress` 流程，批量比较正解与暴力在不同数据规模下的耗时，辅助验证复杂度上界。
- **`std::chrono` 计时模板**：用 `steady_clock` 的 `now()` 与 `duration_cast` 封装成通用计时器，既能测量墙上时间，也能返回毫秒、微秒级结果。
